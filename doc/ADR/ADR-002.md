
# ADR-002 — Use Hexagonal Architecture

## Status

Accepted

## Context

LedgerCore must maintain:

* business correctness
* infrastructure independence
* testability
* long-term maintainability

The project will interact with:

* PostgreSQL
* Kafka
* Redis
* HTTP APIs
* background workers
* observability tooling

Directly coupling business logic to infrastructure frameworks would:

* make testing difficult
* increase refactoring cost
* reduce domain clarity
* encourage framework-driven design

## Decision

Adopt Hexagonal Architecture.

Each module should contain:

* domain
* application
* infrastructure
* presentation

Example:

```text
transfer/
├── domain/
├── application/
├── infrastructure/
└── presentation/
```

Dependency direction:

* domain must not depend on infrastructure
* application orchestrates use cases
* infrastructure implements ports/interfaces
* presentation handles external communication

## Consequences

### Positive

* improved testability
* cleaner domain modeling
* easier infrastructure replacement
* reduced framework coupling
* clearer business boundaries

### Negative

* more initial structure
* more abstractions compared to CRUD architecture
* requires architectural discipline

## Notes

Hexagonal Architecture should remain practical.

Avoid:

* excessive interfaces
* generic abstraction everywhere
* unnecessary indirection
* architecture ceremony without business value
