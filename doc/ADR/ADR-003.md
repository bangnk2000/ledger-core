# ADR-003 — Use Tactical DDD

## Status

Accepted

## Context

Financial transaction systems contain:

* strong business invariants
* state transitions
* consistency requirements
* transactional rules
* auditability requirements

A CRUD-oriented data model would make business logic:

* scattered
* difficult to validate
* hard to evolve safely

## Decision

Use Tactical Domain-Driven Design.

The project will initially adopt:

* Aggregates
* Value Objects
* Domain Events
* Repository abstraction
* Use Case/Application services

Example aggregates:

* Account
* Transfer
* Ledger

Example value objects:

* Money
* AccountId
* TransactionId
* Currency

Example domain events:

* TransferCreated
* TransferCompleted
* TransferFailed

## Consequences

### Positive

* business rules become explicit
* domain language becomes clearer
* invariants remain centralized
* easier future evolution
* event-driven readiness

### Negative

* increased modeling effort
* requires deeper domain thinking
* steeper learning curve than CRUD architecture

## Notes

DDD adoption should remain tactical and practical.

Avoid:

* over-modeling
* premature bounded-context splitting
* excessive abstraction
* unnecessary enterprise ceremony
