# ADR-004 — Use Lightweight CQRS

## Status

Accepted

## Context

The system contains:

* transactional write operations
* reporting/read operations
* different consistency needs

However, the project does not initially require:

* separate databases
* distributed projections
* event sourcing
* independent query infrastructure

Introducing full CQRS too early would:

* increase complexity
* duplicate models unnecessarily
* slow development
* complicate debugging

## Decision

Adopt Lightweight CQRS.

The project will:

* separate command and query responsibilities logically
* keep a shared database initially
* avoid distributed projections initially
* avoid event sourcing initially

Example structure:

```text
transfer/
├── command/
├── query/
```

Command responsibilities:

* transfer processing
* balance updates
* ledger creation
* transactional consistency

Query responsibilities:

* transaction history
* account statement
* reporting
* dashboard views

## Consequences

### Positive

* cleaner responsibility separation
* easier future CQRS evolution
* simpler read optimization later
* reduced initial complexity

### Negative

* some duplicated models may appear later
* read-side optimization remains limited initially

## Future Evolution

Full CQRS may be introduced when:

* reporting complexity increases
* read throughput diverges significantly
* projections become necessary
* analytics workloads expand
